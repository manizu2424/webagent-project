# WEBAGENT.KR 데이터베이스 아키텍처 선택지

## 1. 문서 목적

이 문서는 제품 요구사항과 분리된 DB 의사결정 기록이다. 두 방식 모두 동일한 Next.js 화면, 진단 흐름, n8n 자동화를 지원한다. 차이는 데이터 접근, 인증, 운영 책임과 비용이다.

현재 MVP의 채택안은 **WEBAGENT 전용 PostgreSQL 자체 구축**이다. Supabase는 향후 운영 여건이 바뀌거나 고객 로그인·파일 저장 기능을 빠르게 확장할 때 재검토한다.

## 2. 공통 기술 경계

- Next.js App Router + TypeScript
- n8n이 AI 모델, Telegram, 선택적 이메일 연동 담당
- DB에는 고객, 진단 원본, 구조화된 결과, 상담 정보를 저장
- 브라우저에서 개인정보 테이블을 직접 전체 조회하지 않음
- 공개 결과 URL에는 내부 순차 ID 대신 무작위 UUID 사용

## 3. 시나리오 A: Supabase

```text
사용자 → Next.js → Supabase PostgreSQL → n8n → AI·알림
```

### 장점

- DB, 관리 콘솔, 인증, Storage, RLS를 빠르게 확보할 수 있다.
- 관리자 인증과 향후 사용자별 권한 구현이 쉽다.
- PostgreSQL 기반이어서 자체 DB로 이전할 여지가 있다.

### 비용과 위험

- 외부 서비스 정책·가용성·요금에 의존한다.
- RLS와 service role key를 잘못 다루면 데이터가 노출될 수 있다.
- 이미 VPS 운영 역량이 있으면 비용·편의 이점이 줄어든다.

### 필수 보안 원칙

- 브라우저에는 anon key만 노출한다.
- service role key는 서버와 n8n에서만 사용한다.
- 공개 사용자는 필요한 INSERT만 허용하고 관리자 조회는 RLS로 제한한다.
- 개인정보와 결과 조회는 서버 API 또는 충분히 무작위인 공개 토큰을 통한다.

## 4. 시나리오 B: 자체 PostgreSQL

```text
사용자 → Next.js 서버 API → WEBAGENT PostgreSQL
                         ↘ n8n → AI·알림 → 내부 결과 API
```

### 장점

- 데이터, 스키마, 백업과 비용을 직접 통제한다.
- Contabo·Docker와 n8n 내부 네트워크를 활용하기 쉽다.
- 관계형 고객·상담 데이터와 향후 CRM 확장에 적합하다.

### 비용과 위험

- 업데이트, 장애 대응, 모니터링, 인증, 백업·복원을 직접 책임진다.
- 단일 VPS에 앱과 DB를 두면 장애 영역이 겹칠 수 있다.
- 운영 절차가 지켜지지 않으면 관리형 서비스보다 복구 위험이 크다.

### 필수 운영 원칙

- `webagent-db`와 `n8n-db`를 논리적·가능하면 물리적으로 분리한다.
- PostgreSQL 5432 포트를 외부에 공개하지 않는다.
- 앱과 n8n은 제한된 Docker 내부 네트워크와 최소 권한 계정으로 접속한다.
- 매일 외부 저장소 백업, 일간 7일·주간 4주·월간 6개월 보관을 기본으로 한다.
- 월 1회 복원 테스트와 DB 업데이트 전 수동 백업을 수행한다.

## 5. 비교표

| 기준 | Supabase | 자체 PostgreSQL |
|---|---|---|
| 초기 개발 속도 | 매우 빠름 | 보통 |
| 운영 부담 | 낮음 | 높음 |
| 인증·Storage | 기본 제공 | 별도 구현 |
| 인프라 통제 | 제한적 | 높음 |
| 비용 구조 | 사용량·플랜 기반 | VPS·운영 비용 기반 |
| 백업 책임 | 플랜에 따라 제공 | 직접 구축·검증 |
| 고객 포털 확장 | 빠름 | 직접 설계 필요 |
| 기존 Contabo 활용 | 보통 | 높음 |

## 6. 선택 기준과 현재 결정

Supabase는 시장 검증 속도, 운영 인력 부족, 사용자 인증과 Storage의 조기 필요가 가장 중요할 때 적합하다. 자체 PostgreSQL은 VPS 운영 경험, 데이터 통제, n8n과의 내부 연결, 장기 비용 예측이 더 중요할 때 적합하다.

현재 프로젝트는 Contabo와 Docker를 전제로 하고 상세 PostgreSQL 실행 문서가 존재하므로 자체 PostgreSQL을 채택한다. 이 결정에 따라 제품 문서에서 Supabase 고유 표현은 제거하고, 실제 구현 계약은 `03-PostgreSQL_MVP_개발실행서.md`를 따른다.

## 7. 공통 논리 데이터 모델

| 테이블 | 책임 |
|---|---|
| `leads` | 회사·담당자 연락 정보 |
| `diagnoses` | 입력 원본, 공개 UUID, 처리 상태 |
| `diagnosis_results` | 점수, 추천, 예상 효과, 요약 |
| `consultations` | 상담 요청, 방식, 일정, 영업 상태 |
| `automation_logs` | 개인정보를 제외한 워크플로 이벤트·실패 추적 |

가변적인 도구 목록, 반복 업무, AI 추천과 구축 단계는 JSONB를 사용할 수 있다. 검색·조인·상태 관리에 필요한 필드는 정규 컬럼으로 둔다.
